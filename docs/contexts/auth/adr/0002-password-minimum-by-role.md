# 密码下限按角色分级，而不是全站一条线

`admin` 至少 12 位，普通账号至少 8 位。两档都**只管长度，不管组合**。

## 为什么不是一条线

原来全站统一 12 位，理由是「整站的安全押在一个密码上」。
那句话对 admin 成立，对普通账号不成立 —— 这是两种爆炸半径：

| 账号 | 泄露后对方能拿到什么 |
|---|---|
| admin | 全站配置 |
| 普通账号 | **他自己的**书签和天气城市偏好 |

业务数据本来就按 `userId` 隔离，普通账号之间互相看不见。
用保护整站的标准去要求一份个人书签，成本（记不住 → 写在便签上）高于收益。

## 为什么敢降到 8 位

弱密码的现实威胁是**在线爆破**，而它已经被挡住了：
`LoginThrottleService` 是双维度的，账号维度 5 次/15 分钟就锁 15 分钟，
IP 维度 20 次。8 位密码在这个速率下不可枚举。

离线爆破的前提是先把库拖走 —— 那是另一个威胁模型，答案是 argon2id，
不是再多加四位。

## 为什么不加组合要求

强制大小写/数字/符号只会逼出 `Password1!` 这种熵更低、还更难记的东西。
NIST SP 800-63B 明确反对组合规则和强制定期改密，这里两条都不做。
长度是唯一的规则，所以 `买菜要买西红柿` 和 `coffee-rain-window` 都是合法密码。

## 考虑过但没做的方案

**「敏感信息加密存库 + 密钥分片存别处」**：这解决的是**库被拖走**的威胁，
不解决弱密码 —— 攻击者是正常登录进来的，应用会老老实实替他解密。
而且现在库里没有值得加密的东西：第三方 API key 在 `.env`，不在表里。

等真要往库里存第三方凭据时再做，形态是列级 AES-256-GCM + `.env` 里的密钥，
不需要新机制（密钥不进库、不进仓库，正是 `.env` 已经在做的事）。

## 容易踩的地方

`changePassword` 必须**先查到用户、再按他的角色取下限**。顺序反了的话
admin 会被按 8 位放行，而且完全静默。`user-admin.spec.ts` 里
「admin 同样的 8 位密码会被拒」那条就是钉这个的。
